# Python 開発ガイド

## 目的

この文書は、Python プロジェクトを変更する際の汎用的な実装規約を定めます。
対象リポジトリに `AGENTS.md`、`README.md`、`docs/`、`pyproject.toml`、CI 設定が
ある場合は、そちらを優先してください。この文書は、プロジェクト固有の規約が不足して
いる場合の補助規約です。

## Python コード

### 説明文

本番コードのモジュール、class、関数、メソッドには、日本語の docstring を記載して
ください。説明文は、そのコードが何をするかだけでなく、必要に応じて、なぜその責務を
持つか、呼び出し側が守る前提、副作用、境界条件を判断できる内容にします。

- public、private を問わず、処理を持つ class、関数、メソッドを対象とする。
- docstring の先頭では、役割を簡潔な日本語で説明する。
- 引数、戻り値、例外、外部への副作用、境界条件が自明でない場合は補足する。
- 識別子、環境変数名、外部 API 名、プロトコル名などは翻訳しない。
- 単に別の関数を呼び出すだけの薄いエントリーポイントは、省略してよい。
- テスト関数は、テスト名だけで検証内容が明確な場合は省略してよい。

簡潔な説明で十分な場合は、一文の docstring とします。

```python
def default_target_date() -> date:
    """既定の対象日を返す。"""
```

前提や副作用の説明が必要な場合は、本文を追加します。

```python
def publish(self, output_path: Path, target_date: date) -> str:
    """生成済みファイルを外部ストレージへ保存する。

    呼び出し前に出力先の設定が検証済みであることを前提とする。
    """
```

### 型定義

本番コードの class、関数、メソッドには型定義を必須とします。型定義は、呼び出し側が
入力と出力の契約を判断でき、実装変更時に不整合を検出しやすい内容にしてください。

- 関数とメソッドは、すべての引数と戻り値に型アノテーションを付ける。
- 戻り値がない関数、メソッド、`__init__` には `-> None` を付ける。
- class が保持する属性は、dataclass のフィールドまたは明示的な属性アノテーションで
  型を定義する。
- 複数モジュールで受け渡す構造化データは、dataclass、型付きモデル、または具体的な
  コレクション型で表現する。
- `Any` は、外部ライブラリのレスポンスなど、具体的な型を利用できない境界に限定する。
  変換後の内部データへ `Any` を持ち込まない。
- `dict`、`list`、`tuple` などのコレクション型は、要素型まで記載する。
- 型構文は対象プロジェクトがサポートする Python バージョンに合わせる。

```python
def target_window(target_date: date) -> tuple[datetime, datetime]:
    """対象日の開始時刻と終了時刻を返す。"""
```

### コメント

コードコメントは、コードを読めば分かる処理の逐語説明には使用しません。次のような
判断理由や制約を残す必要がある場合に、日本語で記載してください。

- 外部 API、ライブラリ、プロトコルの仕様により必要な処理
- 誤って変更されやすい時刻、範囲、並び順、互換性などの境界条件
- 一見すると不要に見えるが、冪等性、再現性、後方互換性のために必要な処理
- スキーマ、変換、永続化の責務が分かれている理由

### 責務と依存関係

- 標準ライブラリと既存の依存関係を優先する。
- 新しい依存関係を追加する前に、既存構成で実現できない理由を確認する。
- 外部 API、データベース、ファイルシステム、クラウドサービスなどへの副作用は境界
  モジュールへ寄せる。
- データ変換、バリデーション、フィルタリングなどの純粋な処理は、外部クライアントの
  具体実装へ依存させない。
- 環境変数、設定ファイルの読み込み、既定値、検証は、アプリケーション境界にまとめる。
- 複数モジュールで共有する設定値やドメインデータは、変更しにくい型付きデータ構造で
  表現する。

## 設定と外部パラメーター

コードを変更せずに利用者や運用者が調整する値は、用途に応じて環境変数または設定
ファイルへ分離してください。

- API キー、認証情報、トークンなどのシークレットをコードへ直書きしない。
- 実際の値を設定済みの `.env` ファイルはコミットしない。
- 環境ごとに異なる接続先、ロケーション、プロジェクト ID、保存先などは設定として
  扱う。
- 環境変数や設定項目を追加または変更する場合は、例示ファイル、README、設定読み込み、
  テストをあわせて更新する。
- 同じ用途の設定を JSON、YAML、TOML、環境変数など複数形式で理由なく併存させない。

### YAML 設定

YAML を扱う場合は、安全に読み込み、実行前に検出できる誤りを検証してください。

- `yaml.safe_load()` を使用し、任意オブジェクトの生成を許可しない。
- 必須項目、型、空文字列、重複、構文エラーを検証する。
- 設定項目の意味が分かりにくい場合は、YAML コメントまたは README で説明する。
- YAML の構造や必須項目を変更する場合は、利用者向け文書と関連テストを同時に更新する。

## ログ

ログは構造化ログを前提にしてください。メッセージ文字列を解析しなくても検索、集計、
アラート設定ができる形式を優先します。

- 各モジュールでは `logging.getLogger(__name__)` で logger を取得する。
- ログの JSON 化や formatter 設定は、エントリーポイントや共通設定に集約する。
- 検索対象となる ID、対象日、処理件数、ファイルパス、外部リソース名などは、message へ
  埋め込まず、独立したフィールドとして出力する。
- 時刻はプロジェクトで定めた timezone と形式に統一する。未定義なら UTC の ISO 8601 を
  優先する。
- 例外を記録する場合は、例外情報と stack trace を保持する。
- API キー、認証情報、環境変数のシークレット、個人情報をログへ出力しない。
- 各モジュールで `json.dumps()` した文字列を logger へ渡さず、共通 formatter が変換する
  構成を優先する。

```json
{"timestamp":"2026-06-08T00:00:00Z","severity":"INFO","logger":"app.worker","message":"処理を完了した","target_date":"2026-06-08","rows":120}
```

## テスト

- 動作を変更する場合は、対象を絞った回帰テストを追加または更新する。
- 外部 API、クラウドサービス、データベースなどは通常のテストで呼び出さず、mock、
  fixture、test double、依存注入で表現する。
- 設定ファイルの変更では、正常系に加えて、必須項目不足、型不正、空文字列、重複、
  構文エラーを検証する。
- 時刻や範囲の処理では、開始境界、終了境界、timezone、日付またぎを検証する。
- スキーマや永続化形式を変更する場合は、フィールド名、型、null 許容性、互換性を
  検証する。
- ログ出力を変更する場合は、有効な構造化ログであること、必須フィールドが存在する
  こと、シークレットが含まれないことを検証する。

## 開発ツール

開発ツールと確認コマンドは、対象プロジェクトの設定を優先してください。未整備の
Python プロジェクトでは、次を標準候補とします。

- 依存関係と仮想環境: `uv`
- lint と format: `ruff`
- 型チェック: `mypy` strict mode
- テスト: `pytest`
- タスク実行: `poethepoet`
- commit 時の補助チェック: `pre-commit`

設定は可能な限り `pyproject.toml` に集約し、理由なく個別設定ファイルを増やさないで
ください。通常の開発チェックやレビュー前の確認には、プロジェクトが提供する統合
コマンドを使用します。未整備なら次のような入口を用意することを検討してください。

```sh
uv run poe lint
uv run poe typecheck
uv run poe test
uv run poe check
```

format を適用する場合は、ruff formatter を優先します。

```sh
uv run ruff format
```

実装完了前には、プロジェクトの README、CI、`pyproject.toml`、poe task に従って
必要な検証を実行してください。実行できなかった検証がある場合は、その理由を明記します。
